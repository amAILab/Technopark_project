## Критичные и важные замечания

### 1) Критично: «код подтверждения» хранится на клиенте
**Наблюдение:** в интерфейсе и коде явно задан `11111111` как код подтверждения добавления проекта. Этот код также описан в README.

**Почему это риск:** любой, кто откроет сайт или исходный код, может отправлять записи в Apps Script, если endpoint доступен публично.

**Рекомендация:**
- Убрать «общий секрет» из фронтенда.
- Ограничить запись серверной авторизацией (Google Identity, allowlist e-mail/доменов, signed token, backend proxy).
- Для Apps Script — проверять `Session.getActiveUser().getEmail()` (в корпоративном домене), либо перейти на backend, где секреты не раскрываются клиенту.

### 2) Важно: endpoint Apps Script и ID таблицы жёстко зашиты
**Наблюдение:** URL веб-приложения и ID таблицы указаны в клиенте как константы.

**Почему это риск:** endpoint и структура источника данных легко обнаруживаются и могут использоваться для автоматизированных запросов.

**Рекомендация:**
- Минимизировать публичные идентификаторы (по возможности).
- Ввести rate limit и валидацию на стороне сервера.
- Разделить read/write контуры (чтение — публичное, запись — защищённая).

### 3) Важно: inline CSS/JS в `index.html` ухудшает кэш и сопровождение
**Наблюдение:** в `index.html` присутствуют большие inline-блоки стилей и логики.

**Почему это риск:**
- Сложнее вносить изменения и проводить ревью.
- Снижается эффективность кэширования.
- Труднее внедрить CSP без `unsafe-inline`.

**Рекомендация:**
- Вынести стили в `styles.css`, скрипты в `app.js`.
- Подключать скрипт с `defer`.
- Добавить базовый CSP и постепенно ужесточать.

### 4) Важно: JSONP-механика чтения Google Sheets
**Наблюдение:** чтение данных выполняется через динамическое добавление `<script>` c callback (`gviz/tq`).

**Почему это риск:** JSONP исторически менее безопасен и хуже контролируется политиками безопасности.

**Рекомендация:**
- Рассмотреть переход на более безопасный API-слой (backend proxy / Sheets API через сервер).
- Если JSONP оставляется — жёстко ограничить источники в CSP (`script-src`).

## Средний приоритет

### 5) A11y: улучшить семантику и доступность состояния
- Добавить `aria-live` для блока статуса синхронизации.
- Для переключения представлений добавить `aria-current`/`aria-selected` и связь tab-panel.
- Проверить контраст secondary-текста (`--muted`) и маленьких подписей.

### 6) SEO/SMO: неполные метаданные
- Добавить Open Graph / Twitter Card.
- Добавить `canonical`.
- Добавить `sitemap.xml` (если планируется индексируемый прод-URL).

### 7) UX/данные
- Валидация формы «Новый проект» минимальная: полезно добавить проверки длины, формата, обязательности ключевых полей до отправки.
- Добавить явный индикатор режима: «локальный» vs «подключён к таблице» (частично уже есть, но можно сделать заметнее).

## Быстрый план исправлений (1–2 спринта)

### Sprint 1 (без смены архитектуры)
1. Убрать публичный confirm code из UI/README и временно отключить публичную запись.
2. Вынести inline CSS/JS в отдельные файлы, включить `defer`.
3. Добавить базовый CSP и `Referrer-Policy`, `X-Content-Type-Options` (через hosting config).
4. Улучшить A11y-атрибуты для навигации и статусов.

### Sprint 2 (архитектурное усиление)

2. Добавить server-side валидацию + rate limiting.
3. Настроить централизованный аудит логов добавления/изменения проектов.
